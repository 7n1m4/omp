## Known limitations — execution works; what remains is correctness of the bookkeeping

`f8734ffeb2` removed the silent fake: the no-spawner path in `mission/runner.ts` now assigns `workerError = NO_WORKER_SPAWNER_ERROR` instead of fabricating a handoff, and the status write is gated with `if (!workerError) { f.status = "completed"; }` (`mission/runner.ts:245-247`), so a failed attempt leaves the feature `in_progress` — that guard still protects any direct `runMission` caller that passes no spawner, though `start_mission_run` no longer takes it. `5a0b02df94` wired the spawner: `runMissionWithWorker` (`packages/coding-agent/src/tools/mission.ts:363-370`) passes `spawnWorker: spawnMissionWorker` into `runMission`, so `start_mission_run` (`packages/coding-agent/src/tools/mission.ts:381-392`) drives real work instead of bailing out. Each feature gets one `mission-worker-base` child spawned via `runStructuredSubagent` with the static Handlebars assignment prompt `prompts/agents/mission-assignment.md` (rendered by `renderMissionAssignment`, `mission.ts:~41`) and a `WORKER_HANDOFF_SCHEMA`-validated handoff (`mission.ts:~58`); `toWorkerHandoff` throws on an error, an abort, a nonzero exit, missing or invalid structured output, or a reported `failure`, so a worker that fails keeps its feature unfinished rather than completing it. The abort signal the tool is handed now reaches the runner (`mission/runner.ts:~88,155`) — it previously arrived in the position the code called `_ctx` and was dropped.

Also still live:

- `runValidators` (fixed in `19baf188f8`, `file-service.ts:151-195`) no longer stamps `pass`: it takes an OPTIONAL `spawnValidator` seam and records `status: "fail"` with the reason (no spawner configured, or the validator's own error) instead of an empty pass. Residually, the seam is only filled from the mission tool: `RunMissionOptions.spawnValidator` (`mission/runner.ts:121-125`) is wired by `runMissionWithWorker` (`tools/mission.ts:363-370`) and nowhere else, so a direct `runMission` caller that passes no seam still gets a `fail` "did not run" per validator, which correctly fails the run. The runner has no built-in default validator; `ValidationStatus` is still exactly `"pass" | "fail" | "skipped"` and `mission/types.ts` was not touched.
- `endFeatureRun` (fixed in `19baf188f8`, `file-service.ts:299-322`) no longer marks a feature completed before the scope-growth check: `checkScopeGrowth()` is decided before any write, and the pause branch returns `{ success: true, paused: true, completed: false }` without persisting `completed`, so the feature stays `in_progress`. The two outcomes are mutually exclusive by construction and the return type is unchanged.
- Handoff persistence (was "never persisted to disk under `handoffs/` or `transcripts/`") is fixed in `19baf188f8`: the new `mission/handoff-store.ts` writes one pretty-printed `<missionDir>/handoffs/<slug>.json` per feature (temp file + rename) and the runner persists both the success and the synthesized failure handoff, so handoffs are no longer confined to `progress_log.jsonl`. Two residuals: `initMissionDir` still creates `transcripts/` with nothing ever written into it (only `handoffs/` receives content), and the `handoffs/` store has no fsync and the mission dir has no cross-process lock, so a crash between rename and durability, or two concurrent runs, can still lose or interleave a handoff file. `readLatestHandoff` falls back to `filterWorkerHandoffs()` for mission dirs that predate the store, so pre-`19baf188f8` runs remain readable.
- `readMissionState` swallows read errors and returns a default (`file-service.ts:222-229`); writes are a fixed temp file + rename with no fsync and no lock (`#atomicWrite`, `file-service.ts:46-50`). `19baf188f8` added `readMissionStateSafely` (`mission/runner.ts:28-33`) for the failure path, which returns `null` rather than defaulting when the state file is unreadable: the feature is still reopened and the failure still recorded in `progress_log.jsonl` and the handoff file, but the mission is left between states instead of being paused. The swallowing default and the lockless, fsync-less atomic write are untouched by this commit.
